  genuinely new or changed screens, all on one editable canvas opened in the pen.dev VS Code
  extension or app. Use this whenever the user points at a feature — a GitHub PR, a Linear
  ticket, or a plain-English description — and asks you to "design this using pen", "make a
  pen.dev canvas for X", "create a .pen file for this feature", or otherwise wants a visual
  proposal built as a pen.dev canvas grounded in what the app already has. Also trigger when the
  user wants to explore the current UI for a feature before deciding what to build, if they want
  the output as a `.pen` file. This is a mobile app (Expo / React Native, `apps/mobile`); the
  mockups are pen.dev artboards, not native code. Don't use this for implementing a feature in
  code (that's linear-implement-task) or for pure written research with no visual output.
  Requires the `pen` CLI to be installed and logged in (`pen status`).

# Design a feature (pen.dev canvas)

The goal is a **visual proposal a human can react to and forward**: a `.pen` canvas that puts
the app's current screens next to the proposed ones. A screen that already exists — current, or
a change to it — is a **real screenshot** (the change screenshotted from a throwaway
implementation spike); only a genuinely **new** screen is generated by the pen.dev agent. The
written brief — what changes, what's new, what can be reused — goes in the **conversation,
never on the canvas**. The `.pen` file itself is the editable surface (opened in the pen.dev VS
Code extension or app) — there's no separate "editable canvas" step, because pen.dev's output
already is one. Implementation happens later, in code, against the approved screens.

**The canvas carries only screens and concise titles.** No AI-written thesis, captions,
explanations, rationale, or footnotes — ever. A short factual title per screen plus a
`CURRENT` / `NEW` tag is the whole of the canvas's text. Everything you'd want to say *about* the
design is said in the conversation alongside the file.

Work in this order. Each step feeds the next — skipping the grounding steps produces
generic-looking mockups that ignore the design system and reinvent things the app already has.

---

## 1. Gather the feature context

Resolve whatever the user pointed you at into a concrete picture of the feature.

- **GitHub PR** (`#572`, a PR URL): `unset GITHUB_TOKEN; gh pr view <n> --repo ShopIt-LLC/shopit-monorepo --json title,body,headRefName,files`. Groundwork PRs on this repo often carry a full written map of the current flow in the body (see `fix/thank-you-received-shelf-groundwork` / PR #572) — mine it, it saves you the code archaeology.
- **Linear ticket** (`SHO-123`, a Linear URL): invoke the `linear` skill to fetch the issue description and every comment. Decisions and scope cuts usually live in the comment thread.
- **Plain description**: use it as-is, but ask one or two sharpening questions if the surface area is unclear ("Is this a new tab, or does it live inside an existing screen?").

Then load the guardrails the mockups must respect:

- `.claude/ai/design-system.md` — `Button` and `Input` are standardized and locked; use their real variants/sizes, don't invent new ones.
- `apps/mobile/components/ui/` — the actual primitives (buttons, inputs, sheets, cards).
- Skim two or three existing screens in the same area of the app so the proposal matches established layout, spacing, and navigation patterns rather than a generic mobile aesthetic.

Write down, in a sentence or two: what the feature is, who the user is in that moment, and which flows/screens it touches.

## 2. Map the current UI from the code

Before any simulator work, find the relevant screens and components by reading the repo. This is
free, needs no permission, and tells you exactly what "current state" means.

- `apps/mobile/app/` — routes/screens (expo-router). 
- `apps/mobile/components/` — sheets, cards, heroes, flow pieces.
- Grep for the feature's nouns (`grep -ri "gift" apps/mobile/app --include=*.tsx -l`) and for existing data hooks / Convex queries that already return something close to what the feature needs.

Produce a concrete list: `apps/mobile/app/gift/[giftId].tsx` (the claim screen), `components/sheets/OrderSheet.tsx` (where a received gift is shown read-only), etc. Note any **reuse candidates** — a component, a query, a notification type, a copy string that already exists and is close to what's needed. The feature is almost always "recombine what's there", not "build from zero".

## 3. Capture the current screens as real screenshots

Every panel that will be labelled `CURRENT` / "ships today" on the canvas **must be a real
screenshot from the running app**. Code reconstructions of current screens do not go in the
final canvas. This is a gate for the CURRENT panels — not an optional enhancement. (The
NEW/CHANGED panels never touch the simulator.)

This repo's rule still holds: **never drive, screenshot, or look at the iOS simulator unless the
user explicitly asks you to** (`.claude/CLAUDE.md`). So ask once, up front, framed as required
input — using the screen list from step 2:

> The current-state panels have to be real screenshots. I need to drive the simulator to walk
> these screens and capture them: [list]. OK to go ahead? Or capture them yourself and drop
> them here.

- **Green light**: use the `ios-simulator` skill (backed by `agent-device`) to open the app,
  navigate via its accessibility-tree snapshots, and capture screenshots — including batches of
  several screens in one session. It's far more reliable than driving the simulator by hand with
  raw `idb`/grid-overlay taps (coordinate-guessing against a screenshot is slow and error-prone;
  `agent-device snapshot`/`tap @ref` navigates by the real element instead). Walk to each current
  screen from step 2 and capture it. **Two-user flows** (gifting, follows, notifications): both
  dev accounts are in
  `packages/convex/.env.local` (`DEV_ACC_1_*` / `DEV_ACC_2_*`) — sign in via the dev-only
  "Continue with email" button, act from one account, switch, screenshot the receiving side.
  Dismiss any OS overlay (rating prompt, permission dialog) before the shot. Save PNGs to
  `.claude/skills/design-feature-pen/design-feature-pen-workspace/<feature-slug>/screens/` with names
  that map to the brief (`current-gift-claimed.png`, `current-order-history.png`). Keep this
  simulator session alive — step 5 reuses it to screenshot the CHANGE screens.
- **Declined, or the simulator can't be reached**: you cannot finish the CURRENT panels. Say so
  plainly. Either wait for the user to hand you screenshots, or ship an interim page with those
  panels stamped "reconstructed from code — not verified on device" and tell the user they are
  placeholders until real captures land.

## 4. Decide: what changes vs. what's new

This is the deliverable the user actually asked for. Write it before building the canvas — the
canvas visualizes this breakdown, it doesn't replace it. **The brief lives in the conversation.**
None of its prose is copied onto the canvas (see step 5).

Use this structure:

```
## Design brief: <feature>

**What it is:** <one or two sentences — the user's goal in this moment>

**Current state:** <what exists today for this flow, with file references. If nothing
exists, say so plainly — "there is no thank-you screen today" — that's a valid finding.>

**Changes to existing screens**
- `<screen / component>` — CHANGE: <what's different and why>. Reuses <existing component/prop>.
- ...

**New screens / components**
- `<name>` — NEW: <what it is, where it sits in navigation, what it shows>. Built from
  <existing primitives>. Data comes from <existing query, or "needs a new query">.
- ...

**Reuse notes:** <components, queries, notification types, copy strings already in the repo
that this feature should lean on instead of duplicating>

**Open questions:** <scope ambiguities, anything needing a product call before implementation>
```

Keep every "CHANGE"/"NEW" line tied to a real file or a real design-system primitive. Vague
lines ("improve the layout") are a sign you haven't looked hard enough yet.

## 5. Build the pen.dev canvas

The deliverable is a single `.pen` file: a grid of screens, current next to proposed, built with
the `pen` CLI. Two hard constraints:

> **1. Screens and titles only.** The only text on the canvas is a panel ID plus a concise
> factual title per screen (`A1 · app/gift/[giftId].tsx`, `B2 · Order History`, `C2 ·
> gift_thanked notification`) plus a `CURRENT` / `NEW` tag. No thesis, no legend sentences, no
> captions describing the change, no footnotes, no rationale — nothing an AI wrote *about* the
> design. Say that in every `pen --prompt` you send: label text is a fact, not a sentence. If
> it's a sentence, it belongs in the conversation, not on the canvas. The one exception is the
> user's own commentary block, added on request (see the end of this step) — their words, not
> yours.
>
> **Every panel gets an ID — never skip this.** Letter the rows in canvas order (`A`, `B`, `C`,
> …) and number the columns within a row (`1` for the left/CURRENT frame, `2` for the
> right/NEW frame — both `2` when a row is two NEW frames side by side). Put the ID first in
> each frame's label (`A1 · wishlist/[id].tsx`). IDs make frames referenceable in conversation
> ("redo B2", "swap A1 and A2") without restating the whole title — assign them on the first
> build, not as an afterthought.
>
> **Render the ID/title/tag label as a `note` node, not a plain `text` node.** Same rule as
> above for content (still just the fact — panel ID + title + tag, never a sentence), but the node
> type itself must be `type: "note"` sitting directly above (or below, pick one and stay
> consistent across the canvas) each screenshot frame. Notes render with the pen.dev app's own
> built-in sticky-note styling (amber background, dashed border, "Note" header) — that's a feature,
> not a bug: it reads as clearly separate from the mockup content itself, at a glance, without
> needing custom fill/color properties (which `note` nodes don't support anyway — trying to set
> `fill` on one is a no-op). This applies to every panel label on every canvas, not just the
> optional temporary explanation notes described later in this step.

**Always use the `pen` CLI for this step — never the `mcp__pencil__*` tools**, even when they
appear available. `execute`'s `filePath` argument does not reliably target a new/different file:
when the pen.dev desktop app already has some *other* `.pen` file open (anything the user or a
past session left open), the MCP tools silently attach to that live app session instead of the
file you passed, so your edits land in the user's unrelated open document. This actually happened
once (writing "Row A"/"Row B" into someone's open `pricing-card.pen`) — it was recoverable only
because the intrusion was caught immediately via `get_app_state` and undone with `Delete`. The CLI
has no such foot-gun: each invocation is its own isolated process against the exact file you name.

**Finding the CLI and getting it to actually work:**

- `pen` may not be on `PATH` even when installed — check `bun pm ls -g 2>&1 | grep pen` and
  `ls -la "$HOME/.bun/bin" | grep pen` if a bare `pen status` reports "command not found". A bun
  global install symlinks it to `$HOME/.bun/bin/pen`.
- The `pen` script has a `node` shebang, so `$HOME/.bun/bin` alone isn't enough — a `node` binary
  also needs to be on `PATH` (e.g. `$HOME/.nvm/versions/node/<version>/bin`, matching the repo's
  `.nvmrc`) or every call fails with `env: node: No such file or directory`.
- Combine both once per session: `export PATH="$HOME/.bun/bin:$HOME/.nvm/versions/node/<version>/bin:$PATH"`.
- Before starting: `pen status` — if not authenticated, stop and tell the user to `pen login`. If
  it's not installed at all, stop and tell the user (installation is their call, not yours to run).
- **Always pass `--repo <feature-workspace-dir>`** (the folder containing both `canvas/` and
  `screens/`, e.g.
  `.claude/skills/design-feature-pen/design-feature-pen-workspace/<feature-slug>`). Without it,
  the CLI's own inner agent sandbox blocks it from confirming a `--prompt-file` image actually
  exists on disk — it tries `ls`/`find` around the target directory, gets denied, and gives up
  claiming the image is missing, even though it was attached and the file is real.
- **State the relative image path explicitly in the prompt text itself** (e.g.
  `../screens/current-wishlist-detail.png`, relative to the `.pen` output file), and say the file
  already exists and not to search for it — in addition to attaching it via `--prompt-file`. The
  attachment lets the agent see the image; the .pen schema still needs a real relative path in the
  `fill.url` to actually embed it, so both are required.
- Each `pen` call starts a fresh agent with no memory of earlier calls — when adding a frame to an
  existing row, name the target by its **node name**, not a remembered node id (e.g. "insert a
  vertical frame as a sibling of the A1 column, placed after it, inside the existing top-level
  frame named 'Row A'"), since ids from a previous call aren't known to this one.

Generation is not instant (roughly 1-2 min per simple frame, 3-5+ min for a dense screen) — run
each `pen` call with a generous timeout (10 min) and tell the user upfront it'll take a few
minutes per screen.

Build it incrementally, one `pen` call per new frame, chaining `--in`/`--out` so every call sees
the canvas so far:

```
pen --repo <feature-workspace-dir> --in canvas/<feature-slug>.pen --out canvas/<feature-slug>.pen \
    --prompt "<what to add, including the explicit relative image path if any>" \
    --prompt-file screens/<reference.png> --export canvas/<feature-slug>.png --export-scale 2
```

- First call omits `--in` (starts from an empty canvas).
- Save the running file at
  `.claude/skills/design-feature-pen/design-feature-pen-workspace/<feature-slug>/canvas/<feature-slug>.pen`,
  exporting a fresh `<feature-slug>.png` preview after each call so you (and the user, in
  conversation) can check progress without opening VS Code.
- **Pass prompts the way the pen.dev CLI's own skill asks for them**: describe what the frame is
  and where it sits, don't invent creative detail the CLI's own agent is meant to own (colors,
  spacing, micro-copy) — but *do* state the real constraints that already exist in this repo
  (exact hex values, named components, the panel ID/title/tag), since those aren't invented,
  they're facts from step 1 and 4's grounding.

Render each frame by its kind — from step 4's brief, a screen is CURRENT, a CHANGE to an
existing screen, or a NEW screen:

- **CURRENT frame → real screenshot** (step 3). Pass it with `--prompt-file <path>` and prompt
  something like: *"Place this exact attached image as an image layer in the CURRENT column of
  row A. Above it, add a 'note' type node (not a text node) with the exact content 'A1 · <title> ·
  CURRENT'. Do not redraw or recreate the screenshot — use the image as-is."* Downscale first if
  large — `sips --resampleWidth 640 in.png --out out.png`.
- **CHANGE frame → the real screen with only the delta.** The screen already exists, so a
  from-scratch regeneration is never acceptable — it drifts from the real thing in a dozen small
  ways and buries the one change that matters. Two ways to do it right, best first:
  1. **Implement the change on the mockup branch, run it, screenshot it** (same simulator
     session as step 3). This is the highest fidelity — it *is* the app plus the delta — and it
     shows states a screenshot of today can't (a new filter active, a new row type). It doubles
     as an implementation spike.
     - **Always cut a dedicated branch** off the working branch's `HEAD`, named
       `mockup/<feature-slug>`, and **commit** the spike edits there so the screenshots stay
       reproducible. Commit subject `spike(design): <feature> mockup changes for review
       screenshots`, body noting it is a throwaway visual spike, not for merge. Never PR or
       merge it. Never add assistant attribution (CI gate). On this repo the husky pre-commit
       hook needs `node` on PATH, which this machine lacks — commit the spike with
       `--no-verify`.
     - Keep the edits **client-only**: never touch the shared Convex schema or write junk data
       to the shared dev backend — inject any sample data (a synthetic notification row, a
       stubbed filter result) on the client, and mark it with a `// design spike` comment.
     - The spike needs Metro hot-reload: `cd apps/mobile && bun run start`. On this repo Metro
       needs Watchman or it crashes on the first file change with
       `TypeError ... 'changes.addedFiles'` — if `watchman` isn't installed, `brew install
       watchman`, `watchman watch-project <repo>`, then start Metro. Relaunch the dev build
       (`xcrun simctl launch <udid> mobile.shopit.store.dev`) so it attaches.
     - After screenshotting every CHANGE screen, `git checkout` back to the working branch. The
       `mockup/<feature-slug>` branch stays for re-takes (step 6). Place the resulting screenshot
       on the canvas exactly like a CURRENT frame (image layer, not redrawn), tagged `NEW`.
  2. **Describe the delta to the pen agent instead of implementing it.** Only when the diff is
     too big for a quick spike. Attach the CURRENT screenshot via `--prompt-file` as a
     style/layout reference and prompt the delta directly: *"Using the attached image as a
     reference for the existing layout and style, build the updated version of this screen
     with: <the delta from step 4>."* Let the agent regenerate the full frame rather than
     hand-overlaying pixels — that's what its layout/style tools are for.
- **NEW frame → agent-generated artboard.** No counterpart in the app, so fidelity is to the
  design system, not to a screenshot. Prompt with the step-4 description of that screen
  (unembellished), attach one or two CURRENT screenshots from the same area of the app via
  `--prompt-file` as style reference so it matches established layout/spacing/navigation, and
  name the real constraints: locked `Button`/`Input` variants from
  `apps/mobile/components/ui/`, and the palette from `.claude/ai/design-system.md` (button
  `#D34006`, brand `#FF591F`, ground `#FAF9F7`). Ask for light and dark if the feature needs
  both.

**Then always ask (via `AskUserQuestion`): do they want a personal commentary block on the
canvas?** This is the one block of prose allowed — because the user writes it, not you.

- If yes: they give you the text. Add it with a `pen --in ... --out ... --prompt` call that
  places a text layer at the top of the canvas headed `<Name>'s commentary` (e.g. `Guilherme's
  commentary`), containing their words **verbatim** — quote the exact text in the prompt so the
  agent doesn't paraphrase it, and check the exported PNG afterward to confirm it wasn't altered
  or tightened. Treat each line break they mark as a paragraph break.
- **Always wrap the commentary text in a light, opaque background container** (e.g. `#FAF9F7`
  paper tone or `#FFFFFF`, ~24-32px padding, a subtle rounded corner) in the same prompt that adds
  the text — never leave commentary text floating directly on the bare canvas. Dark ink text
  placed with no background reads as unreadable/low-contrast against the canvas's own backdrop
  (hit this in practice — the user couldn't read a commentary block that had no card behind it).
  If you're adding commentary to a canvas that already has some without this background (e.g. an
  older canvas from before this rule), retrofit it the same way: find the existing commentary
  frame and add the background/padding to it in place, without touching or reflowing the text
  itself.
- If no: leave the canvas as screens-and-titles only.

**Sharing**: open the `.pen` file in the pen.dev VS Code extension (or `pen.dev` app) and use its
own **Share** button to get a link. There's no confirmed behavior for whether a share link
auto-updates when the file changes later — treat it as a frozen snapshot until proven otherwise:
after every redeploy (step 6), tell the user to re-open Share and confirm the link reflects the
latest version before forwarding it.

**Opening the canvas for the user to review**: `open <absolute-path-to-file>.pen` (plain `open`, no
`-a`) does correctly launch/focus the pen.dev macOS app on that file when it's installed — confirmed
by the user seeing the right file and content on the first open. If it's not installed, `open`
fails with "No application knows how to open URL file://...pen" (`kLSApplicationNotFoundErr`); at
that point hand them the absolute path and ask them to use the app's own File → Open, or the VS
Code extension if that's what they use instead (no known CLI one-liner for that either —
`code <file>.pen` needs the `code` CLI on `PATH`, which may not be there).

**Ignore `mcp__pencil__get_app_state` as a signal for what the user is looking at.** It kept
reporting the app's own internal `~/.pencil/documents/<uuid>/pencil-welcome.pen` as the active
editor throughout this session, even while the user's actual frontmost window clearly had the real
target file open and visibly correct (confirmed by screenshots). Don't use it to verify an `open`
call worked, and don't treat its "welcome doc active" report as meaning the real file isn't open —
it's simply unreliable for this. Trust what the user reports seeing on screen instead.

**The live app does not reliably pick up external edits made by the `pen` CLI while the file is
already open in it.** After a `pen --in ... --out <same-file>.pen` call from this skill's step 5/6
loop, the open window can keep showing an older cached state (verified via a stale frame height in
its own inspector panel) even after the user scrolls, zooms to fit, or re-runs `open` on the same
path — none of those force a re-read from disk. The one thing that reliably worked: **fully quit
the pen.dev app and reopen the file from scratch.** No lighter in-app refresh/reload was found; if
the user wants to try one, point them at the app's own File menu ("Revert to Saved" or similar) but
don't assert it exists or works — it's unverified. Tell the user up front, before they go looking
for missed changes, that a full quit-and-reopen is the known-working way to see the latest CLI
edits, so they don't waste time scrolling/zooming first.

## 6. Iterate

Small tweaks: `pen --in <feature-slug>.pen --out <feature-slug>.pen --prompt "<the tweak>"`,
re-export the PNG preview. Structural rethinks (a screen splits in two, the flow reorders):
update the brief first, then re-run the affected frame prompts so brief, canvas, and screenshots
stay in sync.

Every redeploy: remind the user to re-check the Share link is current (see the callout in
step 5) — there's no evidence yet that editing the file pushes to an already-shared link.

**When the app itself changes**, re-capture the affected CURRENT screenshots (step 3), then
`git checkout mockup/<feature-slug>`, rebase or re-apply the spike if it drifted, reload the
app, and re-screenshot every CHANGE screen (step 5) — screenshots are the source of truth for
current *and* changed state, and stale ones defeat the point. NEW frames stay as-is unless the
proposal moved.

Stop when the user says the direction is right. Implementation happens later, in code, against
the approved screens — that's `linear-implement-task`, not this skill.

## Notes

- **The `.pen` file is already the editable surface.** There's no separate "editable canvas"
  step — open it in the pen.dev VS Code extension or app to drag frames around, tweak text, or
  hand-edit anything the agent got close-but-not-quite on.
- **Two-user features** (gifting, follows, notifications) have current-state UI on both sides.
  Decide with the user whose experience the feature is about, screenshot and mock that side;
  note the other side's touchpoints in the brief (conversation, not the canvas).
- **"There is no screen for this today"** is a common and legitimate current state. Each flow
  still needs a CURRENT frame — screenshot the nearest thing the user sees instead (an inbox
  row, an orders-list entry). It's still a real capture, not a reconstruction.
- **Nothing AI-written reaches the canvas.** Titles are factual labels (a filename, a screen
  name, a notification type), never a sentence. All analysis, rationale, and open questions
  stay in the conversation with the brief.
- If the user only wants the written breakdown and no mockups, stop after step 4 and say so —
  don't force the canvas.
